# One-page project workspace

## The owner journey

After sign-in, selecting a project opens its session graph. The header names the
project and retained phase state, dates the latest observation, and offers one
current next action. The phase strip is **Plan → Review & Play → Develop →
Checkpoint**. These are recorded states, not a claim that Codex is currently
running. A pending delivery receipt, native activity and the saved run state are
separate facts.

Select the brain to open its durable project conversation in the inspector. A
message remains a draft until the owner sends it; a sent message waits for its
own ledger receipt and retained reply. The advisory assistant is labelled as
advice and cannot masquerade as the brain or directly execute a control. Select
a task to inspect its short result, saved status, observed activity and evidence;
open its confirmed native Codex task only when a task ID exists. The graph keeps
all active or attention-needing registered tasks visible. Older history is
paginated, and the searchable list gives the same selections without requiring
graph gestures.

Roadmap review, decisions, knowledge, budgets, history and advanced controls
are contextual inspector sections. Each begins with the outcome, what needs
attention and the next step. Full narratives, receipts and source records sit
under **Details**. Existing project URLs remain deep links to the corresponding
inspector section; browser Back and Forward restore selection. A narrow viewport
uses a dismissible inspector sheet and retains every control. Selection,
unsent drafts, graph position and keyboard focus survive ordinary refreshes.
Sign-in and intentional Codex/GitHub links are the only route departures.

The same shell serves strict Harness projects. It does not convert their packet,
admission or acceptance gates into standard Play. Review remains distinct from
Play, and signed owner confirmation remains necessary for each effectful control.

## New standard-phase suggestions

These are editable proposal values, not policy changes. The brain can supply a
bounded `phase.taskOutline`: rows with a title, registered repository and exact
repository-relative files. The outline is planning metadata; it is neither a
task approval nor a verified native worktree. No outline yields a visibly
provisional first-tier suggestion and just one suggested parallel slot. Ambiguous
or overlapping files reduce the suggested parallel count. More than ten tasks
needs an explicit owner-edited allocation or a smaller phase.

| Planned tasks | Token suggestion | Total-task suggestion | Included checkpoint reserve |
| --- | ---: | ---: | ---: |
| 1–2 | 20,000,000 | 3 | 10% |
| 3–5 | 30,000,000 | 6 | 10% |
| 6–10 | 40,000,000 | 10 | 10% |

Parallelism is suggested as at most three independently scoped tasks. New Play
suggests 24 hours and a brain allowance of 30% of the **reviewed** phase token
allocation, capped at 12,000,000 tokens. A larger phase budget remains possible
through explicit editing and exact review. Suggestions never rewrite an existing
mission or paused run. Prior usage observations, gaps, consumed tokens and
allowances remain recorded. A gap makes measured remaining **unknown**, not zero
or an implied free balance. Cooperative checkpoint stops and one-shot native
effect boundaries are unchanged.
In isolated-worktree mode, outline rows are producer candidates and each
repository with outlined producers also needs a separate integration-task slot.
The table does not silently inflate its total-task suggestion: if producers plus
integration slots exceed it, the draft explains the shortfall and exact review
requires the owner to edit the total or split the phase.

## Optional isolated native worktrees

Old missions interpret a missing `authority.repositoryMode` as
`repo_exclusive`. A future all-standard, phase-delegated mission may explicitly
review `isolated_worktrees`. Strict Harness and cross-workspace repository
exclusion remain unchanged. Every scoped repository must permit `open_pr`, since
its integration task must open the phase PR. Within one run and one repository, producers may be
concurrent only when every existing owner has a confirmed native task identity,
a separate native task-metadata observation binds it to a distinct registered
Git worktree, its branch/start commit are pinned, and proposed exact-file scopes
do not overlap. An uncertain create, pending client ID, ambiguous path, missing
worktree proof or stale observation keeps the whole-repository lock. A fresh
native task-metadata observation is also required before preserving an artifact
or verifying a committed source result; its receipt does not refresh on replay.

Producers may edit, test and commit within their exact file scopes. Their source
diff and preserved artifacts must come from **their own** pinned worktree. They
do not merge or open the phase PR. After producers settle, a separately budgeted
integration task combines pinned commits, runs combined checks and opens the PR.
The integration task is not a retry of a producer. Conflicts, drift, missing
evidence, unknown delivery, Pause and budget boundaries stop at a visible
checkpoint. The UI distinguishes the reviewed parallel limit from the number
currently eligible, and separately indicates when the one integration task is
ready. None of these numbers says how many native tasks are running.
An integration PR URL remains a retained worker claim until independent remote
evidence verifies its existence, branch, checks and merge state.

## Verification and rollout boundary

Local qualification covers old deep links, Back/Forward, graph selection and
chat drafts, pending receipts, unknown/blocked states, long histories, project
isolation, keyboard tabs and focus, reduced motion and 320px reflow. Protocol
tests include path overlap and aliases, worktree identity, pending IDs,
one-shot replay, Pause/budget races, cross-workspace ownership, artifact
attribution and integration drift/conflicts. The complete Python and JavaScript
suites plus rendered disposable desktop/mobile checks are required. No GitHub
Actions or paid model service is part of qualification.

Source delivery, PR merge, installation and live qualification are separate
facts. Before installing a new protocol, quiesce older writers, back up private
state and verify the installed revision and host binding. Do not upgrade a live
ledger with mixed-version writers, resume the currently paused run, start Play,
or select `isolated_worktrees` for an existing run as an upgrade side effect.
