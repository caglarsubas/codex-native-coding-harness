# Same-project brain transfer with a continuous foreground handoff

`same_project_host_transfer_phase_v1` is a separate operator-only, version-5
preparation control. It covers one transfer of the existing brain to a new
isolated public host, followed by one new preparation receipt/proposal on the
**same connection that loaded it**. It creates no new pilot project or brain ID.
It does not apply the older public identity-transfer control to an ineligible
unreceipted Play, migrate a recovery claim or reopen an expired run.

## Eligibility and immutable history

Require the complete canceled-Play disposition, its exact closed planning
preflight-refusal lineage and a positively completed, closed maintenance load.
Use the same historical source qualification rules as the successor preparation
phase; never execute old source to interpret that history. Both native project
identities, the single brain, checkout, old bindings, every ledger row/sidecar,
usage vector/high-water amount/gap, original expiry and repository hold stay
unchanged. Unknown historical outcomes and terminal safety remain unknown.

The source is the exact still-issued, reviewed maintenance host, not a retired
endpoint or a guessed directory. Only its selected brain/project may be read.
Repeated native full-history projections and a bounded, complete, self-contained
private JSONL must agree with the latest original interrupted turn. The existing
flat legacy/contiguous paginated validation rules remain intact. Shared homes,
foreign roots, forks, missing records, goals and persisted dynamic capabilities
remain unsupported. Retain one immutable private archive; copy no native database,
credential store, sibling transcript, plugin or complete Codex home.

The destination must independently expose complete empty project, loaded-thread,
active-thread, archived-thread and MCP catalogs. Its separately reviewed source
build must implement exact-ID restoration, enforced policy and subscribe-only
contracts. Stock project/import is not a fallback. Pin the original public launch
manifest, permanent exec claim/status, original process-birth record, current exact
PID/parent/argv/cwd/socket ownership and package/config/directory identities. These
are cooperative local provenance, not vendor trust or process-cleanup attestation.
No host launch, restart, signing bypass or endpoint discovery is provided here.

An already completed **native sign-in on that destination** is supported. Inspect
credential privacy metadata only; never read/hash/copy/delete credential bytes or
request login, logout or refresh. Native token-file rotation is not account identity
or a review timer: verify the same actual non-refreshing native account/routing
hash before each restore, load, assignment, subscription and preparation turn.
Changed account, privacy, host, config or scope fails closed. Original source-home
credential metadata remains under its unchanged historical preservation contract.

## One new review and one connection

Review validity is until scope changes, not a short countdown. Preparing reviews
starts no clock, claim or native write. Preparation explicitly reads metadata and
exports the selected history; backup and status never connect or collect usage.

After separate exact owner confirmation, stopped older writers and verified
private database/sidecar/history backups, claim the existing canonical
same-project phase owner **before connecting**. It is keyed to the original
database identity and Play, independent of directory, source, host or request ID.
Any partial owner, failed or unknown stage permanently fences another phase or
transfer. Existing old phase/load/transfer controls cannot become fallbacks.

On one destination connection, commit separate durable claims before exactly one
native project restore, one metadata-only restricted inspection load and one
membership assignment. Require exact identity/history projection, actual loaded
workspace-write/on-request/user/Code Mode-off policy and complete empty **current**
tracked terminals. Then claim one already-loaded-only subscription on that same
pipe and lend the process-local single-use owner to the existing preparation
sender. No connection close/reconnect, second load/subscription, keeper, model
keepalive, native approval response or automatic cancellation is supported.

The exact new preparation scope has zero workers/repository-write authority,
normally a 24-hour confirmation-started clock and a 10,000-token cooperative
one-turn allowance. It carries both original cumulative usage baselines and
unchanged total/brain/reserve limits. Collect once from the existing exact source
telemetry after subscription; retain provenance and sample times. Gaps, regression,
staleness or changed evidence stop without resampling. The 120-second send freshness
limit is unchanged. This pre-turn observation does not invent the new destination
turn's post-turn usage, which remains uncollected/unknown for later accounting.

Retain the new explicit receipt, inert proposal and native completion separately.
Stop, expiry, drift, permissions or lost acknowledgement retain uncertainty and
close the original connection without retry. Current empty trackers do not prove
historical cleanup. No old receipt, checkpoint, owner release, Resume, worker Play,
merge, run success or pilot acceptance is fabricated.

## Exact reviews and installation boundary

```text
python3 -B -m orchestrator.host_transfer_handoff --platform PLATFORM --workspace WORKSPACE prepare COMPLETED_MAINTENANCE_REVIEW DESTINATION_BINDING ORIGINAL_PUBLIC_LAUNCH_MANIFEST ORIGINAL_LAUNCH_ATTEMPT ORIGINAL_PROCESS_RECORD NEW_PRIVATE_REVIEW_DIRECTORY --maintenance-source EXACT_FROZEN_PR179_SOURCE --duration-hours 24 --max-tokens 10000
python3 -B -m orchestrator.host_transfer_handoff --platform PLATFORM --workspace WORKSPACE backup REVIEW NEW_PRIVATE_BACKUP --writers-stopped
python3 -B -m orchestrator.host_transfer_handoff --platform PLATFORM --workspace WORKSPACE confirm REVIEW --confirm-hash EXACT_NEW_HASH --backup NEW_PRIVATE_BACKUP --writers-stopped
python3 -B -m orchestrator.host_transfer_handoff --platform PLATFORM --workspace WORKSPACE status REVIEW
python3 -B -m orchestrator.host_transfer_handoff --platform PLATFORM --workspace WORKSPACE stop REVIEW --confirm-hash EXACT_NEW_HASH
python3 -B -m orchestrator.host_transfer_handoff --platform PLATFORM --workspace WORKSPACE binding-review REVIEW
```

Save the closed `request`, not its wrapper. The destination binding additionally
pins `identityTransferEvidence` to the same source commit/tree as its public task
backend. Never add that field to an original accepted Play's historical binding.

`binding-review` is an exact **conditional cutover proposal**, not an installer,
native action or approval prompt. Its prerequisite is this exact positively
completed transfer/handoff with both new receipt and proposal. No cutover can
use a partial transfer or native completion alone. A later separately authorized
installation must quiesce the exact dashboard writer, verify fresh private backups,
native membership/host and all review pins, retain old bindings and switch only
the startup binding. It must not drain or replay old notifications. Source delivery
and review preparation do not install source, stop a service or bind the dashboard.

## Qualification

Run the full local Python and JavaScript suites, syntax/AST/diff checks and both
finite compiled-native fixtures:

```text
python3 -B scripts/qualify_canceled_continuation.py --package EXACT_PACKAGE --evidence EMPTY_PRIVATE_DIRECTORY --host-transfer
python3 -B scripts/qualify_canceled_continuation.py --package EXACT_PACKAGE --evidence ANOTHER_EMPTY_PRIVATE_DIRECTORY --transfer-lost-ack
```

The positive fixture uses actual two-home exact-ID restore/load/assignment,
actual policy/current-tracker/subscription reads, and a sandboxed new receipt and
proposal on one original destination pipe. There is no fixture keeper; its delay
exceeds the destination's real one-second idle-unload setting. The negative
fixture injects acknowledgement loss **after** a real load and proves that no
second load, assignment, subscription or turn occurs. The ledger, numeric usage,
original launch journals, expired clock and historical refusal are explicitly
synthetic/injected; all model responses are loopback fakes. No live host,
credential, cloud request, download, paid service or GitHub Action is used.

Source qualification, manual merge, safe installation, exact live review,
application and pilot acceptance remain distinct.
