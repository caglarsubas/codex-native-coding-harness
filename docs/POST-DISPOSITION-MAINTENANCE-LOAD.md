# One new post-disposition maintenance load

The owner separately authorized implementing and qualifying one new load of the
existing v3 brain after canceled-Play disposition. This is not a new pilot
project, host replacement, binding installation or retry of an earlier load.

`post_disposition_maintenance_load_v1` is an operator-only metadata control.
An exact new scope-bound owner confirmation is required after source qualification
and safe installation. A broad load intention, old approval, source delivery or
ordinary dashboard polling cannot confirm an unseen executable review.

## Required lineage

Require all of the following, without modifying old records:

- The complete separately confirmed canceled-Play disposition and its preserved
  original ledger rows, usage/gaps, repository holds, claims and historical binding.
- The original canonical `canceled_play_replacement_load_v1` journal must be
  positively `load_observed_idle`, with a closed connection and exactly its five
  original intent, load claim, acknowledgement, observation and outcome files.
  Unknown/partial/failed/stopped loads cannot use this control as a retry.
- The exact original version-2 planning request must have the complete closed
  pre-subscription refusal lineage described in
  [SAME-PROJECT-LIFECYCLE.md](SAME-PROJECT-LIFECYCLE.md). Its native outcome stays
  unknown. Instrumented records or the allowlisted immutable original PR-176
  source are required; no arbitrary failure text or cleanup assertion suffices.
- The same issued live host PID/birth/argv/cwd, private socket epoch, package,
  restricted config, unchanged native history prefixes, credential metadata,
  brain, checkout and both separately pinned project identities. The exact
  candidate binding file/epoch must be identical to the earlier load and planning
  request. No fallback to historical endpoints, replacement host or rebind.
- No successor planning journal/mailbox or continuous foreground owner, including
  partial ownership. Maintenance and planning share the existing database locks.
  A claimed maintenance attempt also fences competing old-phase planning.

The issued-host metadata helper is factored from the earlier load adapter. Its
original undisposed-state gate remains unchanged. The new caller validates its
own post-disposition context before reading those facts. No old source executes.
Native `auth.json` is metadata-only: never read, hash, copy, refresh or repair its
credential bytes. Status, preparation and backup open no native connection.

## One new maintenance claim

The new canonical journal is keyed to the original ledger identity, brain and
Play command, independent of review path/ID, source revision, endpoint or package.
There are no recursive successors, additional loads or claim migration. A durable
intent precedes the original connection; a durable exact load claim precedes one
fixed `thread/resume` with `excludeTurns:true`, unchanged cwd, workspace-write /
on-request / user approval and Code Mode/goals/apps/plugins/hooks disabled. No
model, effort, provider, arbitrary configuration or command is accepted.

On that same connection, repeated exact identity/latest-original-interrupted-turn,
unloaded status, unknown unloaded policy/tracker, complete empty MCP inventory and
non-refreshing authentication observations precede the load. Already-loaded,
active, permission-wait, changing or unsupported states refuse; they are not
adopted or canceled. Afterwards require repeated actual restricted loaded policy,
idle and a complete empty **current** tracked-terminal inventory. Retain native
acknowledgement and observation separately. Close the original connection.

Any uncertainty or interrupted/lost connection consumes the new claim. No retry,
second connection, automatic native permission response, cancellation, host
replacement, observer reconnect or replay is supported. An explicit Stop creates
only a permanent local fence, not a native cancellation. File-only status never
refreshes the observation or claims that the brain is still loaded.

Closing the connection may unload the brain again. This deliberately bounded
inspection does not provide a keeper, scheduler or durable planning subscription.
It cannot be used to manufacture a later already-loaded prerequisite.

## Expiry, accounting and safety

An expired original phase is permitted **only for this metadata maintenance**,
which starts no model turn and collects no new usage. It does not waive or renew
any planning/execution freshness, allowance, reserve or expiry check. Both the
earlier load's usage snapshot and the later separately retained usage/disposition
remain byte-pinned. Missing usage never becomes zero or a refund.

The original phase remains expired; existing planning, Play and recovery stay
fenced. Loading is not authority to prepare a new mission through a native turn.
The separate [successor preparation phase](SUCCESSOR-PREPARATION-PHASE.md)
may propose a distinct preparation-only clock/scope after positive completion;
it cannot reload, extend the old phase, release holds or activate workers. Its
already-loaded prerequisite is independent of this historical observation.
Expired-phase disposition, future phase/turn authority and actual pilot acceptance
are separate work. No brain receipt, safe checkpoint, closeout or ownership
release is fabricated. Current empty trackers do not establish historical cleanup;
current and historical terminal safety remain unknown.

Save the closed request, not the preview wrapper. Review validity ends on scope
changes, not a short timer. Backups require stopped older ledger writers, private
disjoint paths, verified database integrity/fingerprints/identities and every
original sidecar, disposition fence, binding, predecessor record and issued-host
provenance pin. No backup may overlap the registry, ledger, native home, checkout,
package or reviewed launch directory. This source adds no browser write route.
Strict Harness controls are unchanged.

The same original fixture brain/project/host/binding and old journals remain.
No live credential, host, provider, download, paid service or Action is involved.

Keep source implementation, complete local qualification, manual merge, safe
