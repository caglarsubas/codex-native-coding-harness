# Forward-only readiness-owned load and subscription

The new `codex_readiness_start` signed owner control is a distinct first-phase
public-backend readiness operation. It is not an inspection reload, an upgrade
of an old command, Play, recovery, a binding change or a terminal-safety claim.
The existing version-2 public readiness path remains already-loaded-only.

## One request, one connection

**Review readiness-owned startup** displays the same brain, project/checkout,
binding hash, original latest ended turn, unloaded unknowns or observed loaded
policy, and the bounded impact. Confirm this exact preview once in the existing
authenticated conversation. The review has no timer expiry; source, native
state and private scope changes invalidate it. It cannot survive a server key
change as an unsigned approval. No model output or vague assent confirms it.

Only an empty, unowned, paused schema-1, all-standard first-phase project with
an unchanged reviewed phase-delegated mission qualifies. Strict enrollment,
Brain Stop, workers, packets, decisions, pending/uncertain controls, admission,
successor ownership and unresolved permission requests refuse. Every retained
old readiness request must have its receipt and ended observer or a genuine
separately retained disposition. A failed status alone does not resolve it.

Before local command creation, verify private logical registry/ledger backups
and copied original sidecars. The registry-to-ledger transaction commits an
exclusive canonical ledger/brain/database-identity claim before inserting the
new command. Partial file/database persistence fences all later writers and
replacement requests; changing the request ID, endpoint, directory, timestamp
or source cannot mint a second allowance. Quiesce older writers before rollout.

Only this prospective command receives a version-3 checkout-local pre-Play
handoff. It carries the exact reviewed lifecycle hash before notification.
The original notifier connection repeats project, brain, latest-ended-turn,
non-refreshing account, empty MCP, policy and current tracker metadata. It commits
its separate load claim before at most one fixed `thread/resume`. If already
loaded-idle, it observes without another load. If unloaded, null policy and
unknown trackers remain explicit until independently repeated loaded-idle,
restricted effective policy and complete current empty trackers are observed.

The fixed load uses the same brain/cwd, `excludeTurns:true`, workspace-write,
on-request/user approvals and Code Mode/goals/apps/plugins/hooks disabled.
It sets no model/provider, sends no command and answers no native permission.
No inspection method, allowance, claim or connection is reused or modified.

That **same connection** then captures this binary's actual public schemas and
model catalog through the existing evidence collector, starts one bounded
readiness receipt turn, and remains owned by the existing observer until that
turn ends, attention/failure, shutdown or its fixed 15-minute boundary. This
period starts at sending, not while the owner reads the review. It is not a
phase allowance, provider billing cap, review TTL or new background keeper.
There is no timed handoff to another user action, reconnect, deadline renewal,
second load, recovery fallback or automatic request retry. Closing records the
original native outcome and leaves terminal safety unknown.

The designated brain can only acknowledge the original captured evidence hash
or record a closed catalog error through its existing checkout-local mailbox.
It receives no shared registry/controller/socket privilege. Receipt validation
correlates the prospective handoff, canonical claim, load claim/acknowledgment,
loaded-policy observation, source/build/binding and original command/turn.
Unknown acknowledgments and ended observers cannot be reconstructed or retried.

## Preservation and rollout

Keep every old request, notification, receipt/disposition, inspection claim,
run, consumed usage/high-water/gap, expiry and binding epoch unchanged. Only the
new command, its events, purpose-bound claims/mailbox/observations, and its real
catalog receipt may be added. No old status is reclassified or timestamp renewed.
Polling exposes saved status only and never collects or posts a readiness retry.

Current empty tracked terminals do not establish historical descendants/process
cleanup or whole-terminal safety. Schema/catalog evidence is not account
entitlement, successful worker execution or pilot acceptance. Play still needs
its own exact owner review and confirmation; a readiness turn starts no workers.

Source delivery, manual merge, installation, the new exact owner control,
delivery, brain receipt and pilot qualification remain separate. Back up private
state and stop older writers before installing. Do not automatically notify a
saved request or alter a host/binding during installation.

## Local qualification

Unit fixtures exercise the signed scope-bound review, no-load preview, unloaded
and loaded entry, original evidence/receipt, lost acknowledgments, partial claims,
Pause/Stop races, private backup integrity, foreign bindings, strict exclusion,
legacy version-2 refusal, duplicate confirmations and no rearming with a new ID.

```text
python3 scripts/qualify_public_host_restart.py --readiness-owned --executable EXACT_BINARY --sha256 EXACT_HASH
```

This opt-in fixture uses a separate temporary Unix host/home, one cold loopback
receipt to establish history, one actual readiness load/turn and the original
observer. Its model response and mailbox publication are explicitly synthetic;
it qualifies connection/receipt composition, not live model/tool compliance,
native build trust, account access, terminal safety or pilot acceptance. It makes
no live-host connection or external provider request and reads no credentials.

The local qualification includes 22 focused Python cases, 39 JavaScript suites,
31 web syntax checks and rendered 1440px/320px review checks with no horizontal
overflow or control confirmation. The compiled loopback fixture observed the
actual restricted policy, eight catalog models, one readiness load, one receipt
turn and original observer closure. These are disposable-source results, not a
live receipt or permission to activate the pilot.

Protocol reference: [official app-server lifecycle](https://learn.chatgpt.com/docs/app-server).
The pinned binary's observed behavior and generated schemas, not a changing
documentation default, determine runtime qualification.
